# 業務日報システム（くるむ薬局 札幌店）

薬局の日々の業務日報を Web 画面から入力・承認し、週次の帳票（PDF）として
出力するための Google Apps Script アプリケーションです。

スプレッドシートをデータベース兼帳票テンプレートとして使い、
GAS の Web アプリ（`doGet`）が入力画面を提供します。

---

## 主な機能

- **日報入力** … 処方箋枚数・疑義照会件数・調剤室/冷所の温湿度を日ごとに記録
- **管理に関する事項** … その日の特記事項（自由記述）。帳票の上段F列
- **譲渡・譲受記録** … 医薬品を渡した／受けた記録。**1日に何件でも**。帳票の下段
- **管理基準チェック** … 温湿度が基準外の場合は画面で警告し、帳票では色分け表示
- **担当者マスタ / 管理薬剤師任期** … 名簿と任期を管理し、その日の管理薬剤師を自動判定
- **押印（印影）** … 担当者印・管理者印を PNG 画像として帳票に自動配置
- **承認フロー** … 日報の承認・承認解除、編集ロック（既定 10 分で自動解除）
- **変更履歴** … 操作を監査ログとして記録
- **記録簿ビュー（監査用）** … 1か月ぶんを帳票と同じ書式で通し表示。立入検査でそのまま提示でき、PC からは画面上で直接修正も可能。印刷はサーバーを介さないので待ち時間なし
- **月次の確定** … 月が締まったら PDF に焼いてドライブに残す。訂正が出たら前の版を消さずに版を積み増す

## セットアップ

1. 対象のスプレッドシートを開き、**拡張機能 → Apps Script** を選択
2. `Code.gs` の内容をスクリプトファイルに貼り付け
3. HTML ファイル `WebApp` を新規作成し、`WebApp.html` の内容を貼り付け
4. `Code.gs` 冒頭の `CFG` を自店舗の内容に書き換え
5. 関数 `setup` を **1 回だけ** 実行（必要なシートが自動生成されます）
6. **デプロイ → 新しいデプロイ → ウェブアプリ** として公開

手順の詳細・つまずきやすい点は [SETUP.md](SETUP.md) にまとめています。

## 設定（`Code.gs` の `CFG`）

主な設定項目は以下のとおりです。ID やシート名をロジック側に直接書かず、
すべて `CFG` / `SH` / `COLS` に集約しています。

| キー | 内容 |
|---|---|
| `STORE_CODE` / `STORE_NAME` | 店舗コード・店舗名（多店舗化時はコードで日報を分離） |
| `AUTH_MODE` | `'select'`（名簿から選択・共用端末向け）/ `'google'`（Google アカウントで確定） |
| `WEEK_START` | 週の開始曜日（0=日 〜 6=土。帳票が土曜始まりのため既定は `6`） |
| `BUSINESS_HOURS` | 帳票に印字する営業時間 |
| `RANGES` | 温湿度の管理基準（`null` で基準なし扱い） |
| `LOCK_MINUTES` | 編集ロックの有効時間（分） |
| `SEAL_POLICY.ADMIN_EVERY_DAY` | 管理者印を記録・承認の有無にかかわらず毎日押すか（既定 `true`） |
| `SEAL_POLICY.REUSE_ADMIN_STAMP` | 押印済みシートを複製して使い回すか（出力の高速化。既定 `true`） |
| `PDF` | 用紙・向き・余白。ブラウザ印刷と PDF 出力の唯一の出どころ |
| `TEMPLATE` | 帳票テンプレートの行・列レイアウトと書式 |
| `SEAL_FOLDER_NAME` | 印影 PNG の保管フォルダ名 |
| `TZ` | タイムゾーン（`Asia/Tokyo`） |

`AUTH_MODE` を `'google'` にする場合、デプロイを
**「アクセスしているユーザーとして実行」** に設定する必要があります。

## トリガー

このアプリは **常設のトリガーを使用しません**。すべての処理は
Web アプリからの `google.script.run` 呼び出し、またはエディタからの手動実行です。

ただし、長期間の PDF 出力（`startExport`）は 6 分の実行時間制限を避けるため、
`runExportChunk` を分割実行する方式をとっています。

## 画面の構成

トップバー右側の丸ボタンで画面を切り替えます。選んだ画面だけを表示し、他は隠します。

| ボタン | 画面 | 内容 |
|---|---|---|
| 入力 | 日々の入力 | 本日の状態・週の一覧・入力もれ・入力フォーム |
| 記録簿 | 監査用の記録簿 | 1か月ぶんを帳票と同じ書式で通し表示。直接修正も可能 |
| 確定簿 | 確定した月の一覧 | 月ごとに版が並ぶ。監査ではここから PDF を開きます |
| 名簿 | 担当者の管理 | 担当者・管理薬剤師の任期・変更履歴（中は副タブ） |

4つとも対等な画面で、どこからでも1回で行き来できます。名簿もモーダルではなく画面です。

**切り替えバーは本文の外に置いてあります。** 中に入れると、記録簿や確定簿を出しているときに
本文が短くなり、少しスクロールしただけでバーごと流れて消えてしまうためです。
いまはどの画面でも上に貼り付いたままなので、長い記録簿の途中からでもすぐ移れます。
記録簿や名簿の中のバー（月の移動・副タブ）は、その高さを測って真下に貼り付けています。

書きかけの内容があるまま別の画面へ移ろうとすると確認を求めます。記録簿に未保存の行が
あるときは、記録簿ボタンに目印が付きます。

## 記録簿ビュー（監査用）

トップバーの「記録簿」ボタンから開きます。1か月ぶんを帳票テンプレートと同じ書式で
週ごとに並べるため、**画面の1枚が印刷の1ページ**にそのまま対応します。

- 上部に「対象日数 / 記録あり / 承認済み / 未記録 / 基準逸脱」の集計を表示します
- 管理基準を外れた日は、日付と実測値を一覧で示します
- 既定は**閲覧専用**です。「編集」を押したときだけ値を直せます（画面の色が変わります）
- 印刷は2通りあります（下記）

### 記録は「データ」、確定した月は「PDF」

日々の帳票は**データから毎回描き直します**。画面（記録簿ビュー）がそのまま印刷され、
サーバーへは行かないので待ち時間がありません。

ただしそれだけだと、あとから印影を差し替えたりテンプレートの列幅を変えたりしたときに、
**過去の帳票の見た目まで変わってしまいます**。監査で「これは当時のものです」と言えなく
なるため、月が締まった時点で1回だけ PDF に焼き、それを残します。

| | 実体 | 使う場面 |
|---|---|---|
| 確定前 | データから毎回生成 | 日々の確認、監査での画面提示、訂正 |
| 確定後 | その時点の PDF | 「承認時点でこうだった」の証明 |

出力の入口は2つだけです。

| ボタン | 通る道 | 速さ | 出力先 |
|---|---|---|---|
| 記録簿「印刷」 | `printPaper_()` | **即座**（サーバー往復なし） | プリンタ／ブラウザの「PDFに保存」 |
| 記録簿「この月を確定」 | `startJob_({ fn:'startFreeze' })` | 1週あたり数秒。**月に1回だけ** | ドライブの「業務日報_出力／&lt;年&gt;」 |

用紙・向き・余白は `CFG.PDF` が唯一の出どころです。起動時に画面へ渡し、
ブラウザ印刷の `@page` と縮小率にも同じ値を当てるので、**2つの経路で
刷り上がりが食い違いません**。`CFG.PDF.MARGIN_IN` を変えれば両方が追従します。

画面のプレビューと刷り上がりがずれないよう、次を揃えています。

- 書体は帳票（スプレッドシート）側に合わせた `Arial` 系
- A4 横・1週 = 1ページ
- 紙に入る幅を実測し、はみ出す分だけ縮小（帳票 1031px に対し A4 横は約 1062px なので原寸のまま）
- 画面用の色分け（未記録・承認済・未保存）や操作ボタンは紙に出しません

### 月次の確定

記録簿で月を開くと、その月の状態が上部に出ます。

```
まだ確定できません
  ・確定できるのは最終日(8/31)からです
  ・未記録が 3 日あります
  ・未承認が 1 日あります
```

**確定できるのは、最終日を迎えていて、未記録が無く、全日が承認済みのときだけ**です。
条件がそろうと［この月を確定］が押せるようになり、PDF がドライブに残ります。

月の締めは最終日の営業終了時に行うので、**最終日当日に確定できます**。
その日の記録を保存して承認したあと、そのまま確定まで進められます。

```
業務日報_出力/
  2026/
    2026-08_業務日報_v1_確定20260901.pdf
    2026-08_業務日報_v2_確定20260915.pdf   ← 8/12を訂正して作り直した
```

#### 訂正が出たとき

上書きはしません。上書きすると訂正の痕跡が消え、監査証跡としての価値がなくなります。

1. 記録簿で承認を解除して直す（`変更履歴` に「何をどう直したか」が残ります）
2. もう一度承認する
3. ［確定を作り直す］を押し、**理由を書く**（理由も台帳に残ります）
4. 第2版として積み増す。第1版はそのまま残ります

`変更履歴` と `確定台帳` が対応するので、「v1 と v2 の違いは？」と聞かれたら履歴を出せます。

#### 誤って確定したとき

［取り消す］で **取消** にできます。PDF もドライブの記録も**消しません**。
消してしまうと「間違えて出した」という事実まで消えてしまうためです。
取り消した版の番号は再利用しません（v2 を取り消しても、次は v3）。

### 確定簿ビュー

トップバーの「確定簿」から開きます。確定した月が新しい順に並び、
各月の最新版へのリンクと、過去の版・取り消した版が下に残ります。
監査で「去年の8月を見せて」と言われたときは、ここから開きます。

### 夜間の自動確定

月の締めは最終日の営業終了時に行います。その日のうちに全日の承認まで終わって
いれば、確定に人の判断は要りません。**毎晩1度だけ見にいって、条件がそろって
いる月があれば自動で確定します。**

```
毎晩 23時台
  ├ 止まったままの出力があれば片づける
  ├ ほかの出力が走っていれば、その晩は見送る
  ├ 当月と先月を見る
  │    確定できる → いちばん古い月を1つ確定して、メールで知らせる
  │    月が終わっているのに確定できない → 理由をメールで知らせる
  │    確定済み → 何もしない
  └ 6分で終わらなければ、続きを1分後のトリガーに渡す
```

#### 始め方

エディタで **`setupNightlyFreeze()`** を1回実行するだけです。
やめるときは `stopNightlyFreeze()`、様子を見るときは `nightlyStatus()`。

```
■ 夜間の自動確定
   トリガー : あります（23時台）
   動作     : 有効
   知らせ先 : kanri@kurumu.example.jp

■ 見ている月（2026-09、2026-08）
   ［2026-08］今夜 確定します（第1版）
```

#### 設定（`CFG.NIGHTLY`）

| | |
|---|---|
| `ENABLED` | `false` にすると、トリガーは動いても何もしません |
| `HOUR` | 何時台に見にいくか（既定 23）。営業終了より後にしてください |
| `LOOK_BACK` | 何か月さかのぼるか（既定 2 = 当月と先月） |
| `BUDGET_MS` | 1回の実行で帳票づくりに使ってよい時間（既定 3.5分） |
| `STUCK_HOURS` | 止まった出力を片づけるまでの時間（既定 6時間） |
| `NOTIFY` | 知らせ先。空ならトリガーを作った人のアドレス |

#### 気をつけていること

**6分の壁**　GAS は1回の実行が6分で打ち切られます。1回の実行では
`runExportChunk` を**1度しか呼びません**。2度呼ぶと、1回目が上限いっぱいまで
使ったときに6分を越えて途中で殺され、一時ファイルが残ります。
終わっていなければ、続きは1分後の使い捨てトリガーに渡します。
そのトリガーは、次の実行が**最初に自分を外します**（トリガーは1スクリプト20個まで）。

**気づけないまま止まること**　夜間処理でいちばん困るのは、動いていないのに
動いているつもりでいることです。**できたときも、できなかったときも
メールを送ります。**途中で止まった出力も、6時間を過ぎたら片づけて次に進みます。

**作り直しはしない**　すでに確定済みの月には触れません。訂正して版を積み増すのは、
「なぜ直すのか」を書ける人がやることだからです。

**人の出力を横取りしない**　画面から出力中なら、その晩は見送ります。

#### 決めておいてほしいこと

確定台帳の**確定者欄が「夜間自動」になります**。承認したのは人なので筋は通り
ますが、監査で問われたときに説明できるようにしておいてください。

もう1つ。承認を押し間違えた日があると、その晩のうちに v1 が焼かれます。
翌朝に取り消して v2 を作ることになり、台帳に版が積もります。
それが気になる場合は `CFG.NIGHTLY.ENABLED` を `false` にしてください。
**確定はしないが、確定できる月があることは知らせる**――という使い方はできません
（今のところ通知は確定とセットです）。手で確定する運用に戻してください。

#### トリガーの一覧

| 関数 | 種類 | いつ |
|---|---|---|
| `nightlyFreeze` | 時間主導 | 毎日 `CFG.NIGHTLY.HOUR` 時台 |
| `nightlyFreezeContinue` | 時間主導（使い捨て） | 処理が6分に収まらなかったときだけ、1分後 |
| `sweepStaleLocks` | 時間主導（任意） | 1日1回。期限切れの編集ロックを掃除 |

トリガーの合計実行時間には上限があります（個人アカウント 90分/日、
Workspace 6時間/日）。通常は毎晩数秒で終わり、確定する晩だけ数分です。

### 証跡（ハッシュ）

確定したPDFが「確定した時のまま」かどうかを、あとから確かめられるようにしています。

| 記録 | 中身 |
|---|---|
| `ハッシュ` | PDFそのものの SHA-256。中身が1バイトでも変われば変わります |
| `連鎖` | 1つ前の行の連鎖と、この行（対象月・版・確定日時・ハッシュ）をまとめた SHA-256 |

連鎖があるので、**台帳の古い行をこっそり書き換えると、その行の連鎖が合わなくなります**。
辻褄を合わせるには、それ以降の行をすべて計算し直す必要があります。

`verifyFixes()` で突き合わせます。確定簿ビューの［いま確かめる］からも呼べます。

```
■ 確定PDFの証跡（3 件）
   2026-06 v1 … 一致
   2026-07 v1 … 中身が変わっている … PDFの中身が確定時と違います
   2026-07 v2 … 一致
   ────────────────
   ★ 1 件に問題があります
```

#### これで分かること・分からないこと

分かるのは「**変わっているかどうか**」までです。

- 検出できる … 取り違え、破損、第三者による差し替え、台帳の部分的な書き換え
- 検出できない … **台帳を編集できる人が、ファイルとハッシュを両方書き換えた場合**

ハッシュは同じスプレッドシートの中にあるので、編集権限を持つ人には両方直せます。
本当の意味での否認防止には、時刻認証局（RFC 3161）など**第三者の記録**が要ります。
そこまで求められる運用になったら、確定時にハッシュを外部へ送る仕組みを足してください。

なお `backfillFixHashes()` で後から入れたハッシュが証明するのは
「**入れた時点**のファイル」までです。確定した時点のものである保証にはならないので、
その旨を備考に残します。

### まとめて渡す（ZIP）

期間を選ぶと、その範囲の確定PDFを1つのZIPにまとめます。各月は
「取り消していない最新の版」が入り、SHA-256 を書いた `目録.txt` が同梱されます。

**PDFを1つに結合しない**のは、結合すると別のファイルになり、
**台帳のハッシュがどれとも一致しなくなる**ためです。結合したものは
「元は確定PDFです」を別途保証しなおさなければならず、証跡としては弱くなります。
ZIPなら中のPDFは確定したときのバイト列そのままなので、
受け取った側が `Get-FileHash` などで検証できます。

PDFを作り直さないので、**待ち時間はファイルを読むぶんだけ**です
（12か月ぶんで10〜20秒程度の見込み）。一度にまとめられるのは36か月までです。

### 確定にかかる時間と、その進み具合

長い期間だと数十分かかることがあるため、進み具合は**画面下に固定した帯**に出します。
スクロールしても、ほかの画面へ移っても見えたままです。残り時間はそのジョブの実測から、
まだ0週なら前回までの実績から見積もります。

出力時間のほとんどは**印影の貼り付け**です。1枚ずつシートと往復するうえ、保留していた
書き込みをその場で反映させてしまうため、素直に書くと1週あたり14枚ぶんの往復と、
日数ぶんに分断された書き込みが発生します。次の手当てが入っています。

| 手当て | 内容 |
|---|---|
| 値と印影を分ける | 値をぜんぶ書いて1回で反映させてから、印影を貼る |
| 列のまとまりごとに書く | セルを1つずつではなく `setValues` でまとめる。1週 80回 → 36回 |
| 押印済みシートの使い回し | `SEAL_POLICY.REUSE_ADMIN_STAMP`。押す位置は曜日で決まるので、同じ並びの週は複製で引き継ぐ |

管理者印は記録の有無によらず毎日押されるので、**管理薬剤師の交代日をまたがない限り、
どの週も並びが同じ**です。任期のあいだは押し終えたシート1枚を使い回せます。
交代をまたぐ週だけは並びが変わるため、その週は1コマずつ押します。

複製で画像が引き継がれるかは環境しだいなので、**最初に1枚だけ押して確かめ、駄目なら
1コマずつ押す方式へ自動で戻ります**。どこに時間がかかっているかは
**`benchmarkExport`** で測れます（複製・値の書き込み・印影に分けて実行ログに出ます）。

確定は月に1回なので、ここが多少遅くても日常の運用には影響しません。
日々の印刷はサーバーを介さないため、待ち時間はゼロです。

### 管理に関する事項 と 譲渡・譲受記録

**この2つは別のものです。** 帳票のテンプレート上でも別の欄になっています。

```
上段  A日付 │ B処方箋 │ D疑義照会 │ F【管理に関する事項】│ G-J温湿度 │ K,L印
下段  B〜L結合【譲渡区分/譲渡先名/販売メーカー名称/医薬品名称/包装形態/譲渡数/Lot/使用期限】
```

| | 中身 | 件数 | 置き場所 |
|---|---|---|---|
| 管理に関する事項 | その日の特記事項（設備の点検、事故や苦情、研修など）。自由記述 | 1日1つ | 日報DB の列 |
| 譲渡・譲受記録 | 医薬品を渡した／受けた記録。8項目 | **1日に何件でも** | `譲渡記録` シート |

譲渡は1日に複数件あり得るので、日報DBの列では持てません。日付ごとに別の行として
`譲渡記録` シートに入れ、帳票の下段には1件を1行として並べます。

保存すると、その日のぶんをまとめて入れ替えます（消してから入れ直す）。
中身が1つも入っていない記録は捨てます。

#### 移行

以前は譲渡記録を日報DBの8列で持っていたため、1日1件しか入りませんでした。
移行の手順は下の「ブックを新しい形に合わせる」を見てください。
移行前でも、旧8列に入っている内容はそのまま画面と帳票に出ます（1件として扱われます）。

#### 紙に収まらないとき

帳票の下段は1日1行ぶん（42px）しかありません。譲渡が何件も並ぶとセルの中で
はみ出します。件数が多い月は、**別紙の譲渡記録簿を添える**か、テンプレートの
下段の行の高さを広げてください（1週=1ページの割り付けが変わります）。

### 承認済みの日を直したとき

内容が変わった記録に、前の内容に対する承認印を残すことはできません。そのため
承認済みの日を修正すると、次の2つが必ず行われます。

1. 変更前後の値を「変更履歴」シートに記録する
2. 承認を解除して「入力済」に戻す（管理薬剤師の再承認が必要になる）

画面側でも保存前に確認を求めます。

### 担当者の扱い

既に記録がある日は、その日の担当者を勝手に書き換えません。修正した人は
変更履歴の「操作者」に残ります。別の人の勤務日をあとから入力する場合は、
編集中に担当者印の欄で担当者を選び直してください。

## ブックを新しい形に合わせる

### 新しい関数が見つからないとき

スプレッドシートに貼ってある `Code.gs` が古いままです。**`version()`** を実行すると、
いま貼ってある版とシートの状態が出ます。

```
■ Code.gs の版: 2026-08-31
■ シート
   ［日報DB］16列
   ［譲渡記録］14列
   ［確定台帳］12列
   ［帳票テンプレート］あります
■ 古い列はありません
```

関数の一覧に `version` すら無いときは、貼り替え前の版です。
`Code.gs` の冒頭に、手で実行する関数の一覧を書いてあります。

### なぜ日付を文字列で持つのか

スプレッドシートは、書式を決めていない列に `2026-08` や `2027-03` を書くと、
**日付として取り込みます**。読み戻したときは文字列ではなく日付になっているので、

- 画面の見出しが `Wed 年NaN 月` のように壊れる
- 月で突き合わせている処理（版番号・確定済みの判定・ZIP のまとめ）が全部外れる
- ハッシュの連鎖が合わなくなり、**確定簿の証跡確認が「書き換えられています」と誤検知する**

という壊れ方をします。`Lot` の `007` は `7` になり、`1-2` は日付になります。

そのため次の列は文字列書式（`@`）で持ちます。`updateDatabase()` が設定します。

| シート | 列 |
|---|---|
| 日報DB | 日付 |
| 管理薬剤師任期 | 就任日 |
| 譲渡記録 | 日付 / Lot / 使用期限 |
| 確定台帳 | 対象月 |

すでに日付で入ってしまっている `確定台帳.対象月` は、`updateDatabase()` が
`2026-08` の形に戻します。**ハッシュと連鎖は書き換えません。**
連鎖は書いたときの文字列から作ってあるので、形を戻せば照合はそのまま通ります。
作り直してしまうと、本当に書き換えられたときに気づけなくなります。

### 行の空き

表示形式は「いまある行」にしか付きません。日報DBは1日1行増えるので、
作ったままの1000行だと**3年ほどで書式の外へ出ます**。
そこから先の行が書式を引き継ぐかどうかは環境しだいなので、
`updateDatabase()` が**空きが400行を切ったら 2000 行足します**。

残りは `version()` で見られます。

```
■ 行の空き
   ［日報DB］あと 1968 行
   ［譲渡記録］あと 2000 行
   ［確定台帳］あと 1999 行
```

★が出たら `updateDatabase()` を実行してください。数年に1度の話です。

### 貼り替えたあと

`Code.gs` と `WebApp.html` を貼り替えたあと、**`updateDatabase()` を1回実行**してください。
シートの作成・列の追加・日付の書式・古いデータの移行を、正しい順番でまとめて通します。
何度実行しても同じ結果になります。

```
■ シート
   ［譲渡記録］作りました（14列）
   ［日報DB］列を追加: 管理に関する事項
   ［確定台帳］そろっています
■ 日付の書式
   日報DB.日付 を文字列にしました
   管理薬剤師任期.就任日 を文字列にしました
   譲渡記録.日付 を文字列にしました
   譲渡記録.Lot を文字列にしました
   譲渡記録.使用期限 を文字列にしました
   確定台帳.対象月 を文字列にしました
■ 確定台帳の対象月
   日付になっていた 3 行を 2026-08 の形に戻しました
■ 印影フォルダ
   業務日報_印影（共有しないでください）
■ 譲渡記録の移行
   2026-07-14  譲渡／きた薬局／アムロジピン錠5mg／1箱
   1 件を「譲渡記録」シートへ移しました
■ 残っていること
   日報DBに古い列が 8 つ残っています: 譲渡区分、譲渡先名、…
   中身は移し終えているので、dropLegacyXferColumns で落とせます
```

そのあと **デプロイし直す** と画面にも反映されます。

### 古い列の後片づけ

移行が済むと、日報DBに空の8列（譲渡区分〜使用期限）が残ります。動作に支障は
ありませんが、気になるときは **`dropLegacyXferColumns()`** で落とせます。

**中身が1つでも残っている列は落としません。**先に `updateDatabase()` を実行してください。
列を消すと元に戻せないので、実行前にブックのコピーを取っておくと安心です。

なお、この8列は `COLS.DAILY` に入れていません。入れておくと、落としても
列をそろえる仕組みが作り直してしまうためです（`LEGACY_XFER_COLS` として別に持っています）。

## 困ったとき

### PDFの四隅（外枠）が欠ける

帳票は **1031px = 272.8mm**、A4横・余白0.4インチで印刷できる幅は **1045.7px = 276.7mm** です。
**原寸で収まっている**ので、縮小せずに出力します。

縮小すると帳票の幅が印刷できる幅とぴったり同じになり、外枠が切り取り線の真上に来て
四隅が欠けます。収まっていればその心配がありません。`exportPdf_` が
`checkPrintFit` の判定を見て `fitw` を自動で切り替えます。

### 列幅を変えたとき

1. 帳票テンプレートのシートを直接いじる（画面のプレビューはすぐ追従します）
2. **`checkPrintFit()`** で「原寸で収まります」と出るのを確認
3. **`dumpTemplateLayout()`** の出力を `CFG.TEMPLATE.WIDTH` / `ROW_H` に貼り戻す
   （`buildTemplate()` で作り直したときに同じ形になるように）

```
WIDTH: [104, 50, 50, 50, 50, 327, 58, 46, 54, 46, 98, 98],   ← 合計 1031px
ROW_H: { HEAD1: 42, HEAD2: 42, UPPER: 42, LOWER: 42 },       ← 合計  672px
```

高さは 717px まで使えるので、44px ほどの余裕があります。譲渡・譲受が何件も並ぶ月は、
下段の行を高くすると入りやすくなります（1週=1ページの割り付けは変わりません）。

### 余白を詰める方向は勧めません

**`CFG.PDF.MARGIN_IN` はPDFの余白であって、プリンタが刷れる範囲ではありません。**
多くのプリンタは紙の端から4〜5mmを物理的に刷れないので、ここを詰めすぎると
PDFとしては収まっていてもプリンタ側で切れます。はみ出すときは、まず列幅を詰めてください。
